**Capi-Carpi** is a low-level inference engine written from scratch in **C++17**, with no PyTorch, LibTorch, ONNX or BLAS. It runs a hybrid architecture of **State Space Models (SSM)** and **Sparse Mixture of Experts (MoE)** with **1.58-bit** ternary weights `{-1, 0, +1}`, using **AVX2/FMA** intrinsics, **OpenMP** parallelism and **zero-copy `mmap`** loading, all on a consumer CPU.

| | |
|---|---|
| **Performance** | 236.29 tokens/s (4.23 ms/token) on CPU, on a 23.07M-parameter model |
| **Memory** | Weights mapped with `mmap` in 26.79 ms; 4 ternary weights packed per byte |
| **Dependencies** | None. Only a C++17 compiler with AVX2 support |
| **Development hardware** | Ryzen 7 5700G (16 threads), 32 GB DDR4, no GPU, SATA III SSD |

---

##  Why this project exists

I started with an ambitious question: **can a 1T scale model be trained and run on a home PC with no GPU?** The hardware: 32 GB of DDR4 RAM, 0 GB of VRAM and an ADATA SU650 960 GB SATA III SSD (~600 MB/s).

To try, I combined the most aggressive techniques I found in the literature:

1. **State Space Models:** linear recurrence with constant-size state per token, instead of quadratic $O(N^2)$ attention.
2. **Ternary quantization (1.58 bits):** 4 weights per byte (`uint8_t`), 93.75% less memory than FP32 and no floating-point multiplications in the experts.
3. **Sparse MoE on disk:** `Top-K` routing that activates only a fraction of the experts, which live on the SSD via `mmap`.
4. **Zeroth-order training (MeZO and a variant of my own):** training without backpropagation so activations never need to be stored.

The outcome was twofold. **The inference engine works, is stable and is fast when the model fits in RAM.** And **the I/O math showed that the original goal (1T on this hardware) is physically infeasible**. This repository publishes the former and documents the latter with numbers.

##  Architecture

```text
[Token ID] ──► [Embedding lookup over mmap (zero-copy)]
                          │
                          ▼
        [AVX2 Top-K MoE router] ──► Vectorized softmax
                          │         (IEEE-754 range reduction + degree-6 minimax exp)
              ┌───────────┴───────────┐
              ▼                       ▼
      [Active expert 1]       [Active expert K]
       Ternary SSM 1.58-bit    Ternary SSM 1.58-bit
       4 weights/byte, no      O(1) recurrent state
       multiplications         per token
              └───────────┬───────────┘
                          ▼
     [Weighted fusion + clamping] ──► [AVX2 Fast-Path LM Head] ──► [Logits]
```

**Benchmark topology:** `d_model = 512`, `vocab_size = 16,384`, 8 SSM experts with Top-2 active per token. Total: 23.07M parameters, 9.96M active per token, 73.02 MB on disk.

> **How to read these numbers.** The benchmark runs on a small model whose weights are generated by `model_builder` (not a trained model). The 19.86x speedup comes from removing a 33.55 MB allocation and transposition on every LM Head call (see bug #4), i.e. from fixing an avoidable bottleneck in v1.0.

##  The I/O wall: why 1T doesn't fit on this machine

When the active model fits in the 32 GB of RAM (~35,000 MB/s bandwidth) the engine is fast. When it doesn't, `mmap` pages from the SSD and everything changes:

| Scenario | Calculation | Result |
|---|---|---|
| Inference with experts outside RAM | 3 GB of active weights per token at 600 MB/s | ≈ **5 s/token** physical floor, no matter how optimized the AVX2 code is |
| MeZO training on a 17 GB binary | 2 forward passes (θ+εz, θ−εz) + weight mutation per batch | ≈ **56 s per batch** of pure I/O, about **327 days** for 500,000 iterations |
| SSD wear | Repeated full writes over NAND cells | Premature exhaustion of TBW |

The bandwidth gap is **~58x** between DDR4 RAM and a SATA III SSD, and **~3,000x** against GPU HBM memory. My conclusion: the bottleneck is the storage bus, not the software.

## ️ Four low-level bugs fixed

Without frameworks, I had to diagnose failures that are normally hidden behind them.

### 1. `alignas(32)` inflated pointer strides 4x (`src/tensor/ternary_tensor.h`)
`TernaryWeightBlock` packs 32 2-bit weights into **8 bytes**, but it had `alignas(32)`. Since `sizeof(T)` must be a multiple of `alignof(T)`, the compiler silently inflated it to **32 bytes** (24 bytes of padding). All pointer arithmetic advanced 32 bytes where the generator had written 8: the SSM read 16 MB where there was 4 MB and overran into the next expert's memory. **Fix:** remove the `alignas` and guard the struct with `static_assert(sizeof(TernaryWeightBlock) == 8)`.

### 2. Taylor polynomial divergence in the router softmax (`src/attention/softmax.cpp`)
The first vectorized `exp` used a degree-4 Taylor polynomial around 0 with no range reduction. For $x = -10$ it returns **+291.0** instead of **0.0000454**, so the MoE router gave the highest probability to the worst experts. **Fix:** IEEE-754 range reduction ($x = n \ln 2 + g$), a degree-6 minimax polynomial with FMA (`_mm256_fmadd_ps`) and exponent reconstruction by shifting 23 bits (`_mm256_slli_epi32`). Relative error **< 3 × 10⁻⁷**.

### 3. OpenMP thread starvation with `M = 1` (`src/avx/avx_ops.cpp`)
Parallelizing only the outer `for (i < M)` loop of the matrix multiplication leaves **a single thread working** during token-by-token inference (`M = 1`) while every other core sits idle. On top of that, OpenMP 2.0 (what MSVC provides, for example) does not support `collapse(2)`. **Fix:** manually flatten the `M × N` space into one loop and add a parallel Fast-Path over the `N` columns.

### 4. Cache thrashing from dynamic transposition (**19.86x**) (`src/avx/avx_ops.cpp`)
In v1.0, every `matrix_multiply` call for the LM Head allocated **33.55 MB** with `_mm_malloc` and transposed the whole matrix on every token, causing millions of cache misses. **Fix:** a zero-allocation Fast-Path for `M = 1`. The input vector (2 KB) stays resident in the L1 cache while threads read contiguous rows directly from the `mmap`. Per-token latency: **84.00 ms → 4.23 ms**.

##  Build and reproduce

**Requirements:** a compiler with C++17 and AVX2: `g++` / MinGW-w64 on Windows, or GCC/Clang on Linux.

### Windows (PowerShell)

```powershell
# 1. Build folder
New-Item -ItemType Directory -Force -Path build | Out-Null

# 2. Model generator
g++ -O3 -std=c++17 src/tools/model_builder.cpp -o build/model_builder.exe

# 3. Generate a test binary model (73 MB, 23M parameters)
./build/model_builder.exe --d-model 512 --vocab 16384 --experts 8 --top-k 2 --out capi_test.bin

# 4. Build the engine and benchmark (AVX2 + FMA + OpenMP)
g++ -O3 -std=c++17 -mavx2 -mfma -fopenmp `
    benchmark_capi.cpp `
    src/tensor/mmap_loader.cpp `
    src/utils/transpose.cpp `
    src/avx/avx_ops.cpp `
    src/avx/ternary_ops.cpp `
    src/attention/softmax.cpp `
    src/attention/moe_router.cpp `
    src/attention/ssm_memory.cpp `
    src/attention/ssm_forward.cpp `
    src/model/capi_model.cpp `
    -o build/benchmark_capi.exe

# 5. Run a 200-step autoregressive benchmark
./build/benchmark_capi.exe capi_test.bin 200
```

### Linux / macOS with GCC (bash)

> The Linux commands follow the same scheme; the `mmap` loader uses the POSIX API instead of `MapViewOfFile`.

```bash
mkdir -p build
g++ -O3 -std=c++17 src/tools/model_builder.cpp -o build/model_builder
./build/model_builder --d-model 512 --vocab 16384 --experts 8 --top-k 2 --out capi_test.bin

g++ -O3 -std=c++17 -mavx2 -mfma -fopenmp \
    benchmark_capi.cpp \
    src/tensor/mmap_loader.cpp src/utils/transpose.cpp \
    src/avx/avx_ops.cpp src/avx/ternary_ops.cpp \
    src/attention/softmax.cpp src/attention/moe_router.cpp \
    src/attention/ssm_memory.cpp src/attention/ssm_forward.cpp \
    src/model/capi_model.cpp \
    -o build/benchmark_capi

./build/benchmark_capi capi_test.bin 200
```

### As a dynamic library for Python

```powershell
g++ -O3 -std=c++17 -mavx2 -mfma -fopenmp -shared `
    src/tensor/mmap_loader.cpp src/utils/transpose.cpp `
    src/avx/avx_ops.cpp src/avx/ternary_ops.cpp `
    src/attention/softmax.cpp src/attention/moe_router.cpp `
    src/attention/ssm_memory.cpp src/attention/ssm_forward.cpp `
    src/model/capi_model.cpp `
    -o build/gcapi_core.dll
```

On Linux use `-fPIC -shared` and `-o build/libgcapi_core.so`. The `python/gcapi_wrapper.py` bridge loads the library with `ctypes`.

##  Scope and limitations

- Benchmarks use a 23M-parameter model with generated weights, not a trained language model.
- The engine is designed for models that **fit in RAM**. Beyond RAM, the limit is storage bandwidth (see the I/O wall section).
- x86-64 CPUs with AVX2/FMA only. There is no GPU backend or AVX-512 path.

##  Possible next steps

- Per-component profiling (router, SSM, LM Head) to see where each millisecond goes.
- Test the engine with weights from a genuinely trained SSM/MoE and validate its output against a reference implementation.
- Move the LM Head to lower-precision quantization.
- Train a small model that does fit in RAM using the zeroth-order training variant already developed.

##  What this project demonstrates

End-to-end inference engine design; SIMD vectorization with intrinsics; OpenMP parallelism; virtual-memory I/O with `mmap`; bandwidth analysis and hardware limit reasoning; and debugging of memory-layout, numerical-stability and cache-performance bugs.
